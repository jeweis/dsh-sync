# 5 秒轮询性能（0.4.1）

结论：保留每 5 秒检查的响应速度，优化每轮工作。0.4.0 会对未变化文件反复解析 YAML，并每轮创建、同步和删除锁文件；配置较多时开销明显。

0.4.1 每轮只安全读取 allowlist 文件一次并计算内容哈希，与已验证指纹比较。不解析 YAML、不创建快照对象或配置 AST、不写锁文件、不请求 WebDAV，也不在轮次之间保留配置正文。内容变化先等待静默期和最小间隔，到期后取得跨进程锁，再读取持久状态、重新采集两次、完整校验并确认内容仍满足静默期。只有这些检查通过后才上传。文件路径、符号链接、单文件及总大小限制保留；不依赖文件时间戳，因此同大小、保留时间戳的原子替换也能识别。

## 本机合成配置测量

Darwin arm64、Node 24.20.0，热文件缓存，测量配置未变化时的 `AutoBackup.step()`。全部使用临时 home，网络连接函数设为抛错。旧版每场景 3–10 轮；新版每场景 100 轮，模拟时钟每轮前进 5 秒，实际不等待。耗时为均值，CPU 是进程 CPU 时间除以 5 秒折算的单核比例。

| 场景 | 文件总量 | 原每轮耗时 | 新每轮耗时 | 原 CPU 折算 | 新 CPU 折算 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 1 profile / 3 文件 | 13.9 KiB | 9.1 ms | 0.7 ms | 0.20% | 0.016% |
| 5 profiles / 15 文件 | 556.6 KiB | 169.0 ms | 3.3 ms | 3.75% | 0.081% |
| 10 profiles / 30 文件 | 2235.2 KiB | 916.9 ms | 7.8 ms | 20.22% | 0.179% |

每轮读取量约减半。未变化时 fsync 从每轮 1 次变为 0 次。大场景每 5 秒读取约 2.2 MiB，约 447 KiB/s 的逻辑读取，热缓存下不等同于物理磁盘读取。

100 轮前后主动 GC 后的堆变化分别约 -56 KiB、-1610 KiB、+1 KiB，未见本次样本中随轮次增长的保留堆。基准进程还运行过生成和完整校验，记录中的 RSS 包含这些分配及 Node 保留页，不能视为插件常驻内存，也不能由这次短测证明不存在长期泄漏。

这不是所有设备的性能保证：机械硬盘、网络 home、冷缓存、40 个 profile 或接近 16 MiB 上限的配置需要另测。真正备份时的 YAML 校验、加密和上传仍有相应开销。默认自动备份关闭；关闭或未解锁时不会扫描配置文件。设置页自己的状态轮询不包含在此基准中。调度器在上一轮结束后才安排下一轮，不会重叠堆积检查。

原始结果：[优化前](polling-baseline.json)、[优化后](polling-optimized.json)。复测：

```sh
node --expose-gc scripts/benchmark-auto.mjs --rounds 100
```

回归测试覆盖未变化时无 fsync/远端请求、保留时间戳的同大小替换、无效 YAML 上传前被拦截、观察后取得锁时再发生编辑会重新等待，以及原有防抖、去重、多实例锁、退避、保留策略与离线恢复流程。69 项测试通过；未安装到真实 profile，也未修改 Harness 源码。
