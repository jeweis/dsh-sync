# DSH Sync

- This is an independent Git repository. Do not stage it in the workspace root.
- Resolve the reference Harness checkout from DSH_SOURCE_DIR in the environment or workspace .env. It is read-only; never install, build or generate there.
- Keep machine paths and credentials out of tracked files. Ignore .env and .env.* except .env.example.
- Target Harness 0.2.1-rc.2; keep engines.dsh and Harness peers aligned with the tested runtime. Keep core code independent of Harness runtime imports.
- Tests use temporary homes and a local fake WebDAV server. Never modify a real Harness home or contact a user's remote storage during tests.
- Run npm test, npm run check and npm pack --dry-run before delivery. npm test/prepack rebuild the lazy-CJS browser entry. Do not commit, push or install into a live profile unless requested.
- Settings requests use Connection's authenticated, owner-only exact Fetch route. Never add an online restore action. WebDAV passwords use the Harness credentials provider. Manual passphrases are per-operation; explicit automatic unlock may retain a passphrase only in the host process until disable/unload. Passphrases must not enter persistent files, shared browser stores or response DTOs.
- Snapshots default to encryption; the user-requested plaintext mode requires an explicit setting/CLI opt-in and visible disclosure. Never silently downgrade encrypted reads to plaintext. Rollback journals remain encrypted. Remote data must pass version, path, size and hash validation before any filesystem mutation.
- Automatic backup watches only the snapshot allowlist, debounces/coalesces changes, persists verified content fingerprints, rate-limits attempts and pauses ambiguous uploads. Do not implement automatic or online restore. Keep local settings, credentials, journals and scheduler metadata outside snapshots.
- Retention defaults to 30 per home/device and remote directory/account. Cleanup runs only after a newly verified upload, and only for exact local upload receipts. Check stored object hashes and require strong ETag If-Match DELETE; preserve objects when ownership or version cannot be confirmed. Cleanup errors are warnings, never backup failure. Never adopt legacy or other-device objects based on names or remote device claims.
- User-authorized settings sync is distinct from snapshot restore: apply only explicitly supported live fields through Harness settings APIs with revision checks. Keep sync opt-in, encrypted, conflict-aware and independent of snapshot retention. Never automatically install/remove plugins or replace profile files; unsupported changes remain pending. Snapshot restore remains offline only.

- User-authorized API Key sync is a separate default-off option. Only encrypted live sync may carry provider-bound keys; read/write exclusively through Harness credentials APIs. Never expose values or reusable key fingerprints to browser DTOs or logs. Exclude OAuth grants, environment bundles, WebDAV password and encryption passphrase. Missing keys never revoke another device; file restore remains offline.

- Ordinary reference credentials have no conditional write in rc.2: live sync must never call credentials.set/unset for a provider API-key reference, including empty targets or explicit cloud choices. Keep receiving references pending for manual Harness configuration; never treat a plugin-only mutex, repeated reads or compensating rollback as atomic protection. Record keys still use modifyRecord.

- The user-authorized optional atomic credentials provider may resume automatic reference receiving only through its explicit CAS capability, with manual set/unset and sync CAS sharing the Harness modifyRecord transaction. Never enable or replace a provider in a real profile automatically. All writers of managed references must use this provider; ordinary providers remain manual.

- User-authorized provider onboarding is read-only in the settings page. Provider/profile/credential migration writes are offline CLI-only, requiring a fresh keyed plan token plus --offline and --all-writers-stopped. Share the snapshot restore lock. Rollback preserves current managed Key values/unset semantics via Harness credential APIs, never just re-enables stale legacy keys. Keep journals encrypted, receipts and DTOs free of secrets, and block unsupported/dynamic/shared-external storage layouts.
